Delivery Risk for Jira

Documentation

Reading the board, resolving a conflict, and what the app changes.

Finds blocking dependencies whose dates cannot be satisfied, ranks them by what they take down with them, and reschedules the affected chain in one action.

Nothing is written to Jira until you press Publish.

Getting started

There is no setup. Install the app and open it either way:

  • Apps → Delivery Risk in the top navigation, for the cross-project view
  • The Delivery Risk tab inside a project, for that project's work

On a project tab the query is scoped to that project to start with. Widen it. Cross-project conflicts are the ones nobody owns, and they are most of what this app is for.

The default query looks only at issues that have a blocking link, since those are the only ones that can be in conflict. Edit it freely; it is ordinary JQL. If your Jira cannot filter by link type the app loads all open issues instead and tells you.

The app finds your start-date field on its own. If your Jira has one, issues show as ranges. If it does not, every issue shows as a single day and the app says so.

The left rail is the product. The timeline to its right is the evidence.

Strips are ranked by blast radius, not by size of slip. A two-day conflict that holds up three teams outranks a fifty-day one that holds up nothing.

Fixing a conflict

Press the button on a strip.

Move X → date means one issue moves and nothing downstream is affected.

Resolve — moves N issues means the fix cascades. Pushing one issue back usually breaks the next one down the chain, so the app computes every move the fix requires and tells you the cost first:

4 downstream issues move too, across 2 projects

Each issue keeps its duration. Work is only ever pushed later, never pulled earlier, because that is a scheduling decision the app should not make for you. The blocker never moves; only the blocked side gives way.

Everything stages as a draft. Publish applies it to Jira; Discard drops it and Jira is never touched. A draft survives a page reload.

When the app tells you the answer is incomplete

The app would rather say what it does not know than give you a confident wrong number. Three messages mean exactly that.

Incomplete — more than 1000 issues. A query returning more than 1000 issues is read only as far as the first 1000, so conflicts can exist among the rest. Narrow the query by project or date range for a complete answer.

Incomplete — linked issues could not be loaded. When many dependencies point outside your query, the app pulls the other ends in so the conflicts are visible. That pull is capped, and if it runs out it says how many it missed. Narrow the query so fewer dependencies cross its edge.

Showing the worst 60 of N. The board lists at most sixty conflicts. They are the worst sixty, and resolving them usually clears others downstream, because one upstream fix satisfies many links at once. Narrow the query to work through a team at a time.

More to publish. A large publish is written one issue at a time and has to finish inside a time limit Atlassian sets for apps. If it runs out, it stops rather than being cut off mid-way: whatever it wrote is saved, whatever it did not reach is still staged, and the count tells you how many are left. Press Publish again to finish. Nothing is lost either way.

Edit access. Before offering a fix, the app checks whether you can edit each project the fix would touch, so it does not propose something Jira will refuse. On a query spanning more than 40 projects it checks the first 40, because checking every one is slow, and says how many it skipped. A fix in one of the others may still be refused at publish, and it will say which issue and which project.

Trial. In the last week of a trial the app says how many days are left, once. When a trial ends the board keeps working exactly as it does now and Publish stops, so the worst that happens is you can still see every conflict and have to fix the dates in Jira yourself. Nothing is deleted and nothing is hidden.

The same notice appears, worded differently, if your unpublished changes were staged by a newer version of this app than the one currently installed, which can happen after a rollback. Nothing is lost and nothing is overwritten: the app declines to stage or publish until that version is back, rather than writing the older format over work it cannot read.

Storage. Your unpublished changes live in Atlassian's own storage rather than in the browser, which is why they survive a reload and follow you between machines. If that storage is briefly unavailable, the board still loads live from Jira, but the app will not stage or publish anything until it can read your staged work again. That is deliberate: writing a new change without being able to see the existing ones would overwrite them. Reload in a moment and carry on.

There is also a neutral Note when your Jira cannot filter by link type, and a Setup note when it has no start-date field. Neither is a problem; both say what the app did instead.

Issues pulled in from outside your query

A row marked linked is not something your query asked for. It was pulled in because something in your results depends on it, which is the only way a cross-project conflict can be seen from a project-scoped query. Those rows are shown with a hatched background in the left column.

Unpublished changes you cannot see

The badge counts everything you have staged, including work on issues the current query does not return. When those differ it says so:

3 · 1 not in this view

Publish still applies all of it, which is what you staged. Discard drops all of it too. Widen the query if you want to see the rest first.

Circular dependencies

Jira lets you say A blocks B, B blocks C, and C blocks A. Nothing can satisfy that. The app lists each loop at the top of the board, in ink rather than vermilion, because it is a modelling error and not a date problem. Nothing below a loop can be resolved while it stands.

Explaining the plan

Explain asks for a plain-language read of what is likely to slip and why.

It runs only when you press it, never automatically. It sends the conflicts already on screen to a large language model hosted by Atlassian, so nothing leaves Atlassian's infrastructure. The panel shows what the call cost in tokens.

An explanation is cached against the exact plan that produced it, so opening the same one again is instant and costs nothing. A site can run 100 new explanations a day, which resets at midnight UTC. Past that the button says so and the board carries on working normally. Nobody has hit it in practice; the limit exists so a runaway loop cannot run up a bill.

If the model is busy or slow, the panel says which of those it was and what to do about it. The board never depends on it, so nothing else stops working.

Accessibility

What has been checked, and what has not. Everything below was measured rather than assumed, and the two checkers that measure it ship with the app's source.

Colour and contrast. Every text and colour pair in both the light and dark themes meets WCAG AA, verified by a script that computes the ratios rather than by eye. The one signal colour, vermilion, is never the only thing carrying meaning: a conflict is also marked with a hatched overlap, a left rule, and a strip in the rail that says what is wrong in words.

Keyboard. The whole board works without a mouse. Tab moves between bars, arrows move an issue by a day, Shift by a week, Alt changes its end date, and Enter opens it in Jira. An issue with no dates at all is also reachable: Tab to it and press Enter to schedule it from today, then move it with the arrows. Every button, link and control is reachable and operable, and each one has a name a screen reader can read.

Structure. The page declares its language, has a heading outline with no skipped levels, and the conflict rail is a list of buttons rather than clickable divs.

Motion. The rail's strips slide in when a query runs. If your system asks for reduced motion, they do not.

Target size. Every control is at least 24 by 24 pixels. Two things are deliberately not: a timeline bar, whose width *is* the duration and would lie about the dates if padded, and an issue key sitting inline in a row of text. Both have keyboard equivalents, and every conflict has a button in the rail, so nothing depends on hitting a small bar with a mouse.

What has not been checked

No screen reader has been driven through this app end to end. Accessible names, roles and states have been verified programmatically, which is not the same as confirming how VoiceOver or NVDA actually announce a board of thirty bars.

Windows High Contrast and forced-colours modes have not been tested.

If you hit an accessibility problem, it is a bug and worth reporting. Saying which assistive technology and which version helps more than anything else.

What the app changes

Two fields, on issues you choose, when you press Publish:

  • Due date
  • Your start-date field, if your Jira has one

Choosing the start-date field

Most Jira sites have one date field that means "start", and the app finds it without any setup. Sites with several ("Start date", "Target start", "Baseline start", "Actual start") get a picker in the toolbar, because writing planned dates into the field your team uses for actuals is not something an app should decide for you.

The picker has three kinds of answer:

ChoiceWhat Publish writes
Auto (name)The field the app detected. The default.
A named fieldThat field, and only that one.
Due dates onlyThe due date. No start field is touched at all.

The choice belongs to the site, not to you, so everyone looking at the same board agrees on which field Publish writes. For the same reason only Jira admins (the "Administer Jira" global permission) can change it. Everyone else sees the picker read-only, with the note "Only Jira admins can change this", so they can still tell which field Publish writes.

If the chosen field is later deleted, the app falls back to detection and turns the picker amber rather than carrying on quietly. If it cannot read the setting at all, it publishes due dates only. It never guesses which field you meant.

It never creates, deletes, transitions, assigns or comments on an issue. There is no delete path in the application.

Troubleshooting

"No dependencies to check" — nothing in your query blocks anything else in your query. Widen the JQL, or link issues with "blocks" in Jira.

A conflict I expected is missing — the app treats a same-day handoff as fine. Jira stores dates, not times, so an issue due Monday and one starting Monday is normal rather than broken. Only genuine overlaps are reported.

Issues show as single days — your Jira has no start-date field. Adding a date field named "Start date" (Advanced Roadmaps provides one) gives real durations.

Publish is slow on a large resolution — Jira rate-limits bursts of writes. The app waits and retries rather than failing, so a big cascade can take a few seconds. If Jira keeps refusing it says so and keeps your work staged.

Publish failed for some issues — the reason is shown. Anything that could work on a second attempt stays staged, so pressing Publish again retries it. Issues that no longer exist are dropped, since retrying those would never succeed.

A link type we renamed is not detected — the app recognises Blocks, Dependency, Depends and Requires, and their common renames. Get in touch if yours is not picked up.
