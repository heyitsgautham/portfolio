Delivery Risk for Jira

Security policy

How the app is secured, how to report a vulnerability, and how incidents are handled.

Last updated 22 October 2026.

Delivery Risk for Jira is a Forge app published by Gautham Krishna, a sole developer in India. This page says how the app and the infrastructure behind it are secured, how to report a vulnerability, and what happens when one is found.

Where the app runs

The app has no servers of its own. Its code and its storage run on Atlassian's Forge platform, inside Atlassian's cloud. The manifest declares no permissions.external entries, so the app cannot send data to any outside host, and it loads no remote fonts, scripts or analytics.

Atlassian runs and secures that infrastructure under the Forge shared responsibility model. That covers hosting, network security, encryption of data in transit and at rest, and the isolation of one app from another. Atlassian describes its own controls on its Trust Center.

Access control and authentication

  • There is no separate login. Jira authenticates the user, and the app only opens inside a signed-in Jira session.
  • Every Jira request the app makes is made as the signed-in user, never as the app. The app can only read and change what that user could already read and change in Jira.
  • Before it offers a fix, the app checks that the user may edit every project the fix touches.
  • Only Jira administrators can change which field the app treats as the start date.
  • Staged drafts are stored per user account. One user cannot see or publish another user's draft.
  • Only the developer can deploy new versions, using Atlassian's Forge CLI signed in with his Atlassian account.

Data protection

The app asks for four scopes and no others.

ScopeWhy
read:jira-workRead the issues in your query, their links, and your edit permissions
write:jira-workWrite the new dates when you press Publish
storage:appKeep staged drafts and settings in Forge storage
report:personal-dataReport stored account ids to Atlassian, as every app that stores them must
  • The app reads only the issue fields it needs to draw the timeline: summary, status, due date, issue type, assignee, project, parent, issue links and the start-date field. It does not read descriptions, comments, attachments or worklogs.
  • The app writes to Jira only when the user presses Publish, and only two fields: the due date and the start date. There is no code path that deletes, creates or transitions an issue.
  • Drafts and settings live in Forge storage inside Atlassian, which Atlassian encrypts at rest. Traffic between the browser, Jira and the app uses HTTPS.
  • The app reports the account ids it stores to Atlassian's Personal Data Reporting API and erases data for closed accounts.
  • What is stored, and when it is deleted, is in the privacy policy.

Monitoring and logging

  • The app's backend writes one log line, a count from the personal-data report job. It never logs issue content or account details.
  • Forge records each function call and error. The developer reviews those logs in the Atlassian developer console.
  • Atlassian monitors the Forge platform itself.

Secure development

  • The runtime dependencies are Atlassian's own @forge packages and nothing else.
  • Before each release the developer runs npm audit on those dependencies and the app's own test suite. A release with a known vulnerable dependency does not ship.
  • Forge API tokens used for deploys are personal, kept off shared machines and revoked when no longer needed.

Reporting a vulnerability

Email support@gauthamkrishna.dev with "Security" in the subject line. Include the steps to reproduce and what an attacker could gain.

  • You will get a reply within 2 business days.
  • Please give us a reasonable time to fix the issue before you disclose it.
  • Atlassian's Marketplace security programme can also report vulnerabilities in this app to us, and those follow the same process.

How vulnerabilities are handled

  1. Triage. We confirm the report and rate its severity with CVSS.
  2. Fix. We fix it within the deadlines of Atlassian's Security Bug Fix Policy for cloud apps.
  3. Release. Forge apps update in place, so a fix reaches every customer as soon as it is deployed. Customers do not need to do anything.
  4. Tell the reporter. We confirm the fix with the person who reported it.

How security incidents are handled

A security incident is any event where customer data may have been exposed or changed without permission. We follow Atlassian's incident management guidelines for Marketplace partners.

  1. Contain. Stop the damage first. If needed, that means disabling the affected feature or asking Atlassian to delist the app.
  2. Tell Atlassian. Within 24 hours, through a P1 ticket on Atlassian's ecosystem support portal, with updates at least every 6 hours.
  3. Investigate. Find the cause, how long it lasted, which data it touched and which customers it affected.
  4. Fix. Remove the cause so it cannot happen again.
  5. Tell customers. Affected customers hear what happened and what we did, within 72 hours of the incident being identified where possible.
  6. Review. Write up what happened and what changed, and share it on the Atlassian ticket.
